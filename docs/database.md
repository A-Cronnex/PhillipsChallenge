# Database

## 1. Purpose

This document defines the local and central database responsibilities.

## 2. Database Responsibilities

The local database stores:

- Sites.
- Equipment.
- Observations.
- Conversations.
- Users and local session information.
- Synchronization metadata.
- Local configuration.
- Local map metadata.

The central database stores the synchronized dataset.

## 3. Recommended Local Database

SQLite is the recommended local database technology.

The exact React Native SQLite library must be selected based on:

- React Native compatibility.
- New Architecture support.
- Android support.
- iOS support.
- Migration support.
- Transaction support.
- Performance.
- Maintenance status.

## 6. Timestamps

Use explicit timestamps.

Recommended fields:

- `created_at`
- `updated_at`
- `deleted_at`
- `last_synced_at`

The application must define whether timestamps are stored in UTC.

## 11. Migrations

All schema changes must use migrations.

Do not manually modify the database schema in production.

## 12. Transactions

Operations that create related records must use transactions.

Example:

```
Create observation
    ↓
Create confidence records
    ↓
Create source records
    ↓
Create synchronization record
```

These operations should be atomic.

The database must enforce:

- Required fields.
- Valid enumerations.
- Unique identifiers.
- Consistent relationships.

## 15. Sensitive Data

The database may contain sensitive business information.

The implementation must define:

- Encryption at rest.
- Secure key storage.
- Data deletion.
- Access control.
- Backup behavior.
- Logging restrictions.

## 16. Open Decisions

Resolved since this list was written:

- **Central database technology** → PostgreSQL (`docs/tech-stack.md` §5).
- **Server schema** → `server/migrations/001_initial_schema.sql`; the
  differences from the local schema, and why, are in `docs/sync-api.md` §6.
- **Conflict resolution metadata** → `sync_entity_state` (authoritative
  version and replay key) and `sync_conflicts` (the archived replaced state),
  both server-side. On the device, the existing `sync_records.server_version` /
  `local_version` pair is what the protocol uses.

Still open:

- Exact SQLite library — *(in practice `expo-sqlite`, per
  `docs/tech-stack.md` §3; not re-evaluated.)*
- Encryption implementation.
- Data retention policy — now also covering the server's `sync_conflicts`
  archive, which grows without bound.
- Soft-delete strategy. Still open, but **no longer blocking the download
  direction**: the pull carries creates and updates only, the same restriction
  the upload already had (`docs/sync-api.md` §2). What it still blocks is
  expressing a deletion at all — a record removed centrally stays on every
  device that already holds it.

## 17. Implemented Schema — Migration 001

The nine tables in section 4 are implemented in
`database/migrations/001-initial-schema.ts`, applied by
`database/migrator.ts` and opened through `database/connection.ts`.
Shared enumerations live in `types/domain.ts`.

### 17.1 Conventions Adopted

| Question left open above | Decision taken | Reason |
|---|---|---|
| Timestamp timezone (§6) | ISO-8601 **UTC** strings in `TEXT` columns | A field device can change timezone between capture and synchronization; local-time strings would reorder history when it does. `TEXT` sorts correctly lexicographically and stays readable in a debugger. |
| Identifier type (§5) | `TEXT` UUID, generated by the application | The same id must survive synchronization and identify the record on the server (`docs/offline-sync.md` §7). |
| Enumeration enforcement (§14) | `CHECK` constraints | SQLite has no enum type, and the AI pipeline is an untrusted producer (`CLAUDE.md` §7); values must be rejected at the persistence boundary, not only in application code. |
| Schema versioning (§11) | `PRAGMA user_version`, one transaction per migration | Built into SQLite, needs no extra table. DDL is transactional, so a failed migration leaves no partial schema. |

### 17.2 Deliberate Omissions

- **No `deleted_at` column anywhere.** The soft-delete strategy is still
  open (§16) and adding the column would imply one. It is an additive
  `ALTER TABLE` once decided.
- **No `CHECK` on `observations.operational_status`.** Its allowed values
  are not enumerated in any document; `docs/ai-agent.md` §7 shows only
  `unknown`. Constraining it would mean inventing a vocabulary
  (`CLAUDE.md` §8).
- **No `last_synced_at` anywhere.** Confirmed as device-level state, not a
  per-record column: the download cursor lives in `local_settings` under
  `sync.pull_cursor` (migration 002), and holds the server's own change
  sequence rather than a local clock (`docs/sync-api.md` §2).
- **No encryption.** `CLAUDE.md` §15 requires the protection of sensitive
  local data to be documented, and §18 lists the encryption
  implementation as unresolved. The database file is currently stored
  unencrypted by `expo-sqlite`.

### 17.3 Additions Beyond the Documented Attribute Lists

Three columns are not in the attribute lists of `docs/domain-model.md`
but were required to implement relationships that document already
defines. They are called out here rather than added silently:

- `observations.conversation_id` — implements "Conversation produces
  Observation" (`docs/domain-model.md` §12). Nullable, since an
  observation may also be entered through a plain form.
- `observation_sources.reference` — filesystem pointer to the captured
  artifact, mirroring `conversations.transcript_reference`. Without it an
  image-sourced observation cannot be traced back to its photo.
- `created_at` / `updated_at` on `users`, `conversations`,
  `observation_sources`, `attribute_confidence`, `sync_records` and
  `map_regions` — application of the timestamp rule in §6 to every table.

### 17.4 Nullability Chosen for the Offline Capture Flow

`observations.equipment_id` is **nullable**. Capture must not block on
resolving which existing equipment record an observation belongs to
(`CLAUDE.md` §6); duplicate detection runs after the observation is
already persisted and links it then. `observations.site_id` is
`NOT NULL` — an observation with no site cannot be placed on a map or
attributed to a customer.

### 17.5 Delete Behaviour

`ON DELETE RESTRICT` is used for every reference from a child business
record to its parent (`equipment.site_id`, `observations.site_id`,
`observations.equipment_id`, `observations.created_by`,
`conversations.user_id`). Deleting a site must never silently destroy the
equipment and observations recorded at it (`CLAUDE.md` §6).
`CASCADE` is used only for rows wholly owned by an observation
(`observation_sources`, `attribute_confidence`).

### 17.6 `sync_records` Is a State Table, Not an Operation Log

`UNIQUE (entity_type, entity_id)` means one row per entity, holding its
*current* pending state. Retrying a failed upload updates that row and
cannot enqueue a second one, which is what makes retry idempotent
(`docs/offline-sync.md` §7). The consequence is that this table does not
preserve a history of operations — if an audit trail of every sync
attempt is required, it needs a separate append-only table.

`entity_id` has no SQL foreign key because it is polymorphic. Referential
integrity for that column is the repository layer's responsibility.

### 17.7 `map_regions` Schema Is Inferred

`map_regions` appears in section 4 but has no attribute list in
`docs/domain-model.md`. Its columns were derived from the requirements in
`docs/offline-sync.md` §12 (track download progress, errors and
completion locally) and cover a bounding box, a download status, progress,
error and size. **This schema is not confirmed** and should be reviewed
against MapLibre's actual offline region API before the maps feature is
built.

It records map cache state only. Downloading a region does not download
business data (`docs/offline-sync.md` §11), and this table must never be
read as a statement about which sites or equipment are available offline.

## 18. Implemented Schema — Migration 002

`database/migrations/002-local-settings.ts` adds one table, `local_settings`
(`key`, `value`, `created_at`, `updated_at`).

It exists for a single current purpose: holding this installation's stable
device id, which the server uses to tell a retried change from a new one
(`docs/offline-sync.md` §7). Section 2 above already names "local
configuration" as something the local database stores, but section 4 lists no
table for it, and device-level state has no natural home among nine per-entity
tables.

Two things it deliberately is **not**:

- **Not the sync cursor's home yet.** §17.2 records that the incremental-sync
  cursor is still proposed. This table gives that decision somewhere to land;
  it does not make it (`docs/sync-api.md` §2).
- **Not a place for secrets.** The table is unencrypted like the rest of the
  database. The device id is a random UUID identifying an installation to the
  sync server — not a credential (`CLAUDE.md` §15).
